## Decision (ADR-lite)

**Context**: PR #37 is an epic that bundles 10 finding-level commits squashed into one
merge commit. The `release.md` style guide says "one bullet per merged PR", but it was
written for v0.7.0-style releases where every PR is itself granular. v0.7.1 is
structurally different: one PR carrying epic content.

**Decision**: Keep the 10 finding-level bullets from `[Unreleased]` and tag each one
with `(#37) (f62e2a1)` to preserve the PR+sha7 traceability half of the rule. Bullets
remain organized by emoji category (Fixes / Documentation / Refactor / Maintenance).

**Consequences**:

- Readers see release content at the work-unit granularity that v0.7.0 set as
  precedent (8 PRs → 8 bullets there; 10 findings → 10 bullets here).
- All bullets share the same PR+sha7 tag, which is slightly redundant but signals
  "everything in this release lives in the same epic-PR".
- Future single-PR epics should follow the same pattern; future multi-PR releases
  continue to use one bullet per PR.

## Technical Notes

- `bump-version.mjs` writes Cargo.lock since v0.2.0 hotfix (memory: `release-v020-experience`).
- `gh pr merge --squash` is server-then-client two-step; if the post-merge local
  checkout aborts (memory: `release-v070-experience`, observed again on PR #37 today)
  the server merge already landed — do `git reset --hard origin/main` to align.
- Husky `pre-push` runs the full 8-step `npm run ci` locally before push, so the cloud
  CI failure surface is narrow.
- Release notes are extracted verbatim from the `## [0.7.1]` body — no markdown
  rendering hooks. The body should be reader-facing, not contributor-facing.
- v0.7.0 release notes serve as the closest precedent for tone and structure.
