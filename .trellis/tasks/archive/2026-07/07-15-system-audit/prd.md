# 全维度项目深度审计与优化路线

## Goal

从用户真实痛点、产品需求、UI/UX、架构、模块设计、代码质量、测试、文档、验收、边界约束和长期可维护性出发，对当前仓库做一次可追溯、可复核的系统审计，形成量化评分、问题清单和分阶段优化路线，使项目的长期代谢率能够持续高于腐朽率。

## Confirmed Facts

- 本项目为 single-repo，Trellis 规范层包括 `architecture`、`backend`、`frontend`。
- 当前分支为 `main`，审计开始时存在一项用户已有改动：`.codex/config.toml`。
- 本任务只授权规划、只读取证和审计文档写入；未授权修改产品代码、依赖、数据或发布状态。
- 用户要求使用一手资料研究痛点，使用 Keel 审计架构，使用 codebase-design 审计 Module 深度，并在确有产品取舍需要时通过文档化访谈对齐。
- `README.md` 将 Eyezen 定位为低打扰、跨平台的桌面护眼应用，支持 Windows、macOS 和 Linux。
- 已声明功能包括 20-20-20/Pomodoro、全屏/离开/进程白名单/工作日跳过、统计与 Eye-Care Index、多屏提醒、托盘、全局热键及中英主题切换；这些声明仍需由实现与测试逐项核验。
- 当前技术栈为 Tauri 2 + Rust 2021 + Svelte/Vite/Tailwind/ECharts，使用 SQLite/sqlx 做本地持久化，并包含平台特定依赖。
- `package.json` 提供 `check`、`ci`、`test`、`test:coverage`、`format:check` 等检查入口；README/CHANGELOG 中的覆盖率和资源占用声明在实际运行前不计为已验证事实。
- 最近版本为 v0.7.1，CHANGELOG 声明 v0.7.x 已处理大文件拆分、IPC timeout、权限收窄、macOS 全屏探测和覆盖率门槛；审计需验证其约束是否仍可持续执行。

## Requirements

- 建立覆盖需求与痛点、产品定位、UI/UX、架构、代码质量、测试、文档、验收、边界约束、安全与隐私、性能与资源、发布工程、可维护性和创新体验的审计框架。
- 每项重要结论必须关联仓库文件、代码位置、测试/命令输出、Git 历史或一手公开来源；无法验证的内容必须明确标为未知。
- 采用统一评分口径给出总分和分项分数，区分“能力存在”“有自动化守卫”“有持续趋势证据”，避免仅凭文件数量或主观观感评分。
- 痛点研究只使用官方文档、标准、规范、原始研究或第一方平台资料；每项产品建议都应追溯到用户痛点、证据和项目定位。
- 架构审计采用“架构 = 被持续执行的约束 × 可追溯的理由链”，识别承重主路径、Surface 稳定性、单一事实源、所有权、依赖方向、负路径、时间轴和可失败守卫。
- Module 审计统一使用 Module、Interface、Implementation、Seam、Adapter、Depth、Leverage、Locality 术语，识别浅 Module、泄漏的 Interface、无真实变化点的 seam 以及越过 Interface 的测试。
- 建立当前排熵基线：抑制项、跳过测试、公共 Surface、概念增长、重复事实、所有权新鲜度、旁路、横向依赖、手改派生产物；没有历史趋势时不得伪造趋势结论。
- 问题按证据、影响、发生条件、根因、优先级和修复建议记录；建议优先删除、收敛或深藏复杂度，避免增加兜底分支、兼容残留和投机抽象。
- 给出分阶段路线图，每项建议包含预期收益、成本/风险、依赖、验收方法、回滚或删除条件、建议 owner；区分立即修复、短期深化和长期治理。
- 补充必要功能和低复杂度创新建议，但不得脱离产品定位或凭空扩大产品 Surface。
- 将本次分数定义为当前仓库的内部健康基线；另行给出不计入当前总分的发布门禁建议。

## Acceptance Criteria

- [x] 生成一份主审计报告，含执行摘要、审计方法、证据边界、总分、分项评分、问题清单、优化路线和剩余未知。
- [x] 形成完整仓库清单：运行入口、主要 Module、外部依赖、数据/配置持久化、构建发布链、测试类型和文档来源均可定位。
- [x] 痛点研究文档中的重要外部主张均带可访问的一手来源链接，并明确“证据支持”与“产品推断”的区别。
- [x] UI/UX 审计覆盖首次使用、日常主路径、提醒/打断、暂停与恢复、设置、托盘/后台、错误/空状态、可访问性和平台一致性。
- [x] 架构章节回答 Keel 诊断矩阵全部问题；无证据项作为发现记录，不以解释性文字填空。
- [x] Module 章节列出主要 Interface、Seam 和 Adapter，至少对高风险候选执行删除测试、Interface 测试面检查和依赖分类。
- [x] 实际运行仓库提供的相关 lint、typecheck、test、build、smoke 或等价检查；未运行或失败项明确说明原因和风险。
- [x] 排熵章节给出可复现的当前快照命令/口径，并明确哪些指标因缺少历史样本只能作为基线。
- [x] 所有 P0/P1 发现均有直接证据、根因链、最小修复切片和可验证成功标准；P2/P3 建议不得与其重复计数。
- [x] 所有体验/创新建议均关联痛点、核心主路径、Surface 成本和“不做什么”，避免功能堆砌。
- [x] 审计产物不覆盖或混入 `.codex/config.toml` 的既有用户改动，不修改产品行为。

## Out of Scope

- 未经单独授权实施产品代码修复、重构、依赖升级、数据迁移、发布或提交。
- 不通过主观推测宣称真实用户规模、留存、健康疗效或生产环境可靠性。
- 不提出整库重写；结构问题必须收敛为最小可重写/可删除切片。

## Open Questions

- 无阻塞规划的问题。执行中若发现仓库无法回答的产品取舍，只询问一个最高价值问题，并同步更新本 PRD。
