# 全维度项目深度审计设计

## 1. 目标与边界

本任务交付的是“可复核的内部健康基线 + 独立发布门禁建议”，不是产品代码修复。审计以当前工作树为对象，但不读取秘密文件、不覆盖 `.codex/config.toml` 的已有改动，也不把 README、CHANGELOG、徽章或历史任务中的声明直接当作实现事实。

外部研究、仓库实现、自动化检查和推断必须分层记录：

1. **外部事实**：一手机构、标准、平台文档或原始研究明确支持的主张。
2. **仓库事实**：当前文件、调用点、配置、测试、Git 历史或实际命令输出。
3. **推断**：由事实导出的产品或架构判断，必须注明推断链。
4. **未知**：当前证据无法回答的事项；不以猜测填充。

## 2. 交付物

- `research/user-pain-points.md`：用户痛点、健康证据、平台/可访问性/隐私约束和产品启示。
- `audit-report.md`：主审计报告、评分、问题登记、排熵基线、修复路线、体验创新和发布门禁。
- `prd.md`、`design.md`、`implement.md`：需求、方法和可执行检查计划。

不额外建立平行的事实文档。研究文档拥有外部事实，主报告引用它；源代码与规范拥有实现事实，主报告用路径和命令引用，不复制形成第二套权威规则。

## 3. 审计主路径

审计只走一条承重路径：

`用户痛点/项目定位 → 功能与质量约束 → 当前实现/守卫证据 → 差距与根因 → 最小修复切片 → 可执行验收`

任何建议若不能落回这条路径，归为备选灵感而非路线图事项。任何新概念、Interface、配置项或功能建议都必须说明它消除的歧义、替代/删除的旧概念和不做什么。

## 4. 评分模型

总分 100，定位为内部健康基线：

| 维度                  | 权重 | 核心问题                                         |
| --------------------- | ---: | ------------------------------------------------ |
| 需求证据与产品范围    |   10 | 痛点、目标用户、核心任务和非目标是否可追溯       |
| UI/UX 与可访问性      |   12 | 主路径是否低打扰、可控、可恢复且跨平台一致       |
| 架构约束与理由链      |   15 | 承重主路径、所有权、依赖方向和守卫是否真实存在   |
| Module 深度与代码质量 |   15 | Interface 是否小而完整，复杂度是否集中并可测试   |
| 正确性与测试          |   13 | 行为、负路径、时间轴和平台差异是否由有效测试覆盖 |
| 安全、隐私与平台边界  |   10 | 权限、IPC、输入、持久化和敏感数据约束是否最小化  |
| 性能、资源与可靠性    |    8 | 后台应用的 CPU/内存/IO/启动/恢复行为是否有证据   |
| 文档、验收与发布工程  |    8 | 声明、代码、检查和发布流程是否一致且可复现       |
| 可维护性与排熵能力    |    9 | 删除、迁移、所有权、趋势和减法机制是否可持续     |

每个维度按 0–5 级评分后乘权重：

- 0：关键能力缺失、与声明矛盾或无法形成可用主路径。
- 1：只有意图/文档，或实现高度临时化且无可靠验收。
- 2：能力已实现，但约束分散、负路径或验证明显不足。
- 3：核心行为有测试/验收，主要约束能够定位。
- 4：关键约束有可失败的自动化守卫，异常与时间轴闭合。
- 5：跨平台/生产证据与历史趋势持续证明约束有效，并有主动减法机制。

分数之外单列证据置信度：A（当前实现、检查和必要运行证据完整）、B（实现与检查可核验，但缺实机/趋势）、C（主要依赖声明或静态推断）。未知项降低置信度，不自动判零；已确认的缺失或矛盾才扣分。

## 5. Keel 架构审计

### 5.1 承重主路径

从实际入口追踪“配置载入 → 计时/活动与上下文探测 → 提醒决策 → 用户动作 → 统计持久化/投影 → 托盘与 UI 更新”。确认所有功能是否下沉到这一条路径；若出现平行状态机、重复调度或双写，作为结构发现。

### 5.2 Surface 分级

对 Tauri commands/events、持久化 schema、配置模型、跨 Module Interface、内部实现和装配代码分为四级稳定性。枚举新增字段、flag、option、事件名、错误文本和顺序等显式或事实合同，检查是否处于最便宜的可用层级。

### 5.3 单一事实源与所有权

追踪默认值、枚举、状态、事件、统计口径、版本和权限的拥有者及派生路径。识别重复事实、手改派生产物、横向依赖和“两个 owner/无 owner”的文件或规则。

### 5.4 负路径与时间轴

逐项回答 denied、failed、partial、stale、cancelled，以及重复执行、半途重启、事件重放、休眠/唤醒、时钟变化、多屏热插拔和平台探测失败。只接受当前实现确实会发生的外部失败处理；反对用默认值或静默兜底掩盖内部逻辑错误。

### 5.5 可失败守卫与排熵

检查导入/权限/schema/coverage/格式/发布等守卫能否捕获植入违规。建立抑制项、跳过测试、公共 Surface、概念数、重复事实、所有权新鲜度、旁路、横向依赖和手改派生产物的当前快照；只有 Git 历史存在一致口径时才报告趋势。

## 6. codebase-design Module 审计

统一使用 Module、Interface、Implementation、Seam、Adapter、Depth、Leverage、Locality 术语。

1. 枚举承重主路径上的主要 Module 及其 Interface，包括调用者必须知道的顺序、错误、配置和性能事实。
2. 对候选执行删除测试：删除后复杂度消失的是 pass-through；复杂度扩散到多个调用者的才具有 Depth。
3. 检查 Interface 是否也是测试面；若测试越过 Interface 依赖内部状态，记录 Module 形状问题。
4. 将依赖分类为 in-process、local-substitutable、remote-owned、true-external；只在真实存在两个 Adapter 时承认 seam。
5. 深化建议采用替换而非叠层：命名新的小 Interface、被隐藏的复杂度、应删除的旧浅 Module/测试和新的行为验收。

## 7. UI/UX 与产品审计

以首次启动、配置、日常等待、预警、正式提醒、开始/跳过、暂停/恢复、全屏/离开/白名单跳过、托盘、统计反馈、错误/空状态、退出/重启为任务流。检查：

- 打断是否可预期、可解释、可推迟/跳过且不诱导内疚；
- 智能跳过是否透明，用户能否理解“为什么没有提醒”；
- 统计是否避免把健康建议伪装成医学诊断或精确疗效；
- 键盘、焦点、对比度、缩放、动效、屏幕阅读器和多屏是否可用；
- 平台原生习惯、托盘生命周期、权限提示和后台行为是否一致；
- 新建议是否提高主路径体验，而不是增加配置 Surface。

## 8. 问题登记与修复路线

每项发现使用统一记录：`ID / 严重度 / 维度 / 事实证据 / 触发条件 / 用户或工程影响 / 根因链 / 违反的约束 / 最小修复切片 / 验收方法 / 建议 owner / 删除或复查条件 / 置信度`。

- P0：数据损坏、严重安全/隐私风险或核心主路径不可用。
- P1：常见路径高影响错误、跨平台主要功能失效或架构约束持续失守。
- P2：有限条件缺陷、明显维护成本、守卫或文档缺口。
- P3：体验精修、低风险减法和可选创新。

路线分为立即止损、短期深化、长期治理。禁止整库重写；任何结构建议必须命名最小可替换切片、保持的合同、依赖枚举方式和旧入口删除路径。

## 9. 发布门禁（不计入当前总分）

单列 Windows/macOS/Linux 安装与升级、首次启动、托盘/后台、全屏、多屏、休眠唤醒、系统权限、资源基准、可访问性、签名/打包、回滚和隐私声明门禁。未实测的平台明确标为未验收，不由单平台绿色结果外推。

## 10. 风险与回滚

- 本任务不修改产品行为，因此回滚仅涉及删除本任务新增审计文档；不得触碰用户已有改动。
- 命令若会安装依赖、更新 lockfile、启动 GUI/后台进程或访问外部系统，执行前另行确认。
- 检查失败保持原样记录，不通过跳过、降阈值、抑制或新增兜底使其变绿。
